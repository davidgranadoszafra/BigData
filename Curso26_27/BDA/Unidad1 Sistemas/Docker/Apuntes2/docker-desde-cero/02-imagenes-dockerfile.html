Construir tu propia imagen con un Dockerfile

Hasta ahora has usado imagenes de otros (nginx, ubuntu, hello-world). Ahora construyes la tuya, con tu propio codigo dentro.

1. Una imagen es un monton de capas apiladas

Cada instruccion de un Dockerfile crea una capa nueva encima de la anterior — como un mapa de capas en un editor de imagen. Docker guarda cada capa por separado y la reutiliza si no ha cambiado, en vez de reconstruirla de cero. Esto tiene una consecuencia practica muy real que veras en la seccion 4: el orden de las instrucciones en el Dockerfile importa para la velocidad de build, no solo por estetica.

2. Un Dockerfile minimo, real, explicado linea a linea

Imagina una app Python muy simple: app.py que imprime un saludo. Este es el Dockerfile completo para empaquetarla:

dockerfile - Dockerfile minimo 
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]
1
FROM python:3.12-slim

La imagen base sobre la que se construye todo. slim es una variante reducida de la imagen oficial de Python — menos megas, menos superficie de ataque.

2
WORKDIR /app

Crea (si no existe) y se mueve a /app dentro de la imagen. Todo lo que venga despues (COPY, RUN, CMD) se ejecuta desde ahi.

3
COPY requirements.txt . + RUN pip install ...

Copia SOLO el fichero de dependencias primero, e instala. Por que no todo el codigo de golpe: lo explica la seccion 4.

4
COPY . .

Ahora si, copia el resto del codigo (todo lo que hay en la carpeta actual del host) a /app dentro de la imagen.

5
CMD ["python", "app.py"]

El comando que se ejecuta cuando arranca un contenedor de esta imagen — no cuando se construye la imagen, sino cada vez que haces docker run.

3. Construir y ejecutar tu imagen

bash - Build y run 
docker build -t mi-app:1.0 .
docker run mi-app:1.0

-t mi-app:1.0 le pone nombre y version a la imagen (el "tag") — sin esto, tendrias que referirte a ella por un identificador largo y feo. El . al final le dice a Docker "el contexto de build (donde buscar el Dockerfile y los ficheros a copiar) es esta carpeta".

4. Por que el orden importa — la cache de build en accion

Vuelve al Dockerfile de la seccion 2. requirements.txt se copia e instala ANTES que el resto del codigo, a proposito. Compara los dos escenarios:

Cambias solo app.py

La capa de COPY requirements.txt . y RUN pip install no cambio — Docker reutiliza esa capa de la cache, sin reinstalar nada. El build tarda segundos.

Si hubieras puesto COPY . . primero

Cualquier cambio en cualquier fichero de codigo invalida esa capa — y todo lo que venga despues, incluida la instalacion de dependencias, se repite desde cero cada vez. El build tarda minutos, siempre.

INFO
Regla practica: pon primero en el Dockerfile lo que cambia poco (dependencias) y al final lo que cambia mucho (tu propio codigo). Docker invalida la cache desde la primera capa que cambio hacia abajo — nunca al reves.

5. Que deberia quedarte claro al cerrar este capitulo

  • Un Dockerfile es una lista de instrucciones, cada una crea una capa reutilizable.
  • docker build -t nombre:version . construye; docker run nombre:version ejecuta.
  • El orden de las instrucciones no es cosmetico: dependencias antes que codigo propio, siempre que puedas.
