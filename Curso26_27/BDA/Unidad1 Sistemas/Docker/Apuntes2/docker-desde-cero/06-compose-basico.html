06

Compose: levantar varios contenedores a la vez

Ya sabes crear redes, volumenes y contenedores a mano. Ahora, la herramienta que declara todo eso en un solo fichero en vez de una lista de comandos que hay que recordar.

1. El problema que Compose resuelve

Para levantar una app con su base de datos a mano, necesitas: crear una red, arrancar la base de datos con sus variables de entorno y su volumen, arrancar la app conectada a esa misma red con sus propias variables... y recordar exactamente esos comandos, en ese orden, cada vez. Docker Compose describe todo eso en un fichero de texto y lo levanta con un solo comando.

2. Un docker-compose.yml minimo, real

yaml - docker-compose.yml 
services:
  app:
    build: .
    ports:
      - "8000:8000"
    environment:
      DB_HOST: db
    depends_on:
      - db

  db:
    image: mariadb:11.4
    environment:
      MARIADB_ROOT_PASSWORD: secreto
      MARIADB_DATABASE: miapp
    volumes:
      - datos_db:/var/lib/mysql

volumes:
  datos_db:

Compara esto con todo lo que ya sabes de capitulos anteriores:

En el YAML Equivale a
services Cada bloque es como un docker run distinto — app y db son dos contenedores.
build: . docker build automatico, usando el Dockerfile de esta misma carpeta.
ports El -p del capitulo 1.
environment El -e del capitulo 3.
volumes (dentro del servicio + al final del fichero) El -v nombre:destino del capitulo 4, con el volumen declarado explicitamente.
Sin docker network create en ningun sitio Compose crea una red propia para este proyecto automaticamente. app ya puede hablarle a db por su nombre — el capitulo 5, gratis.

3. Los comandos del dia a dia

bash - Ciclo de vida con Compose 
docker compose up -d          # construye lo que haga falta y levanta todo
docker compose ps             # estado de los servicios de ESTE proyecto
docker compose logs -f app    # logs de un servicio concreto, en vivo
docker compose down           # para y elimina los contenedores (los volumenes se quedan)
docker compose down -v        # lo mismo, pero borra tambien los volumenes -- cuidado
WARN
depends_on no espera a que el servicio este listo, solo a que arranque. En el ejemplo, app puede intentar conectarse a db antes de que MariaDB haya terminado de inicializarse por dentro. Es un fallo muy comun al empezar con Compose — la solucion real (healthcheck + condition: service_healthy) esta en el siguiente capitulo.

4. Que deberia quedarte claro al cerrar este capitulo

  • Compose no es magia nueva — declara en YAML los mismos run, -p, -e, -v que ya conoces.
  • Crea una red propia automaticamente: los servicios se hablan entre si por su nombre, sin configurar nada.
  • depends_on solo controla el orden de arranque, no si el servicio ya esta "listo" de verdad.
