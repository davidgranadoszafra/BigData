Compose avanzado: healthchecks y .env

El capitulo anterior dejo un problema sin resolver: depends_on no espera a que el servicio este listo de verdad. Aqui se arregla, y se ordenan las variables de configuracion.

1. El problema exacto, primero

depends_on: [db] solo garantiza que Docker arranca el CONTENEDOR de db antes que app. No garantiza que MariaDB, por dentro, ya haya terminado de inicializar la base de datos y este aceptando conexiones. Ese hueco de tiempo — el contenedor esta "arrancado" pero el servicio de dentro no esta "listo" — es donde app falla al conectar en el primer intento.

2. Healthcheck: definir que significa "listo" de verdad

yaml - docker-compose.yml con healthcheck 
services:
  app:
    build: .
    depends_on:
      db:
        condition: service_healthy

  db:
    image: mariadb:11.4
    environment:
      MARIADB_ROOT_PASSWORD: secreto
    healthcheck:
      test: ["CMD", "healthcheck.sh", "--connect"]
      interval: 5s
      timeout: 3s
      retries: 10

healthcheck le dice a Docker COMO comprobar si el servicio esta realmente listo (aqui, un script que trae la propia imagen de MariaDB para probar la conexion). Docker repite esa prueba cada interval, hasta retries veces, y marca el contenedor como healthy solo cuando pasa. El cambio clave esta en depends_on: ya no es una simple lista — condition: service_healthy hace que app espere de verdad a que db este sano, no solo arrancado.

3. Variables de configuracion en un fichero .env

Poner contrasenas directamente en el YAML no es buena idea, y menos si el fichero se sube a un repositorio. Compose lee automaticamente un fichero .env en la misma carpeta:

.env
DB_PASSWORD=secreto_real
DB_NAME=miapp
docker-compose.yml
environment:
  MARIADB_ROOT_PASSWORD: ${DB_PASSWORD}
  MARIADB_DATABASE: ${DB_NAME}

.env nunca deberia subirse al repositorio (va en .gitignore) — normalmente se acompana de un .env.example con las mismas claves pero sin valores reales, como plantilla para quien clone el proyecto.

4. Que deberia quedarte claro al cerrar este capitulo

  • depends_on a secas solo ordena el arranque; condition: service_healthy espera a que el servicio funcione de verdad.
  • healthcheck define, con un comando real, que significa "estar listo" para ese servicio concreto.
  • Las contrasenas y configuracion sensible van en .env (fuera del control de versiones), no escritas a mano en el YAML.
