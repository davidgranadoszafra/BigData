Qué es REST, de verdad

  • cliente / servidor
  • verbos HTTP
  • códigos de estado
  • statelessness

Cliente, servidor, y un "recurso"

Cuando abres una web o una app, tu ordenador (el cliente) le pide cosas a otro ordenador (el servidor) a través de la red. En REST, cada cosa que puedes pedir se llama un recurso — un usuario, un pedido, una foto — y cada recurso tiene una dirección única: una URL. /usuarios/5 no es "una función que se ejecuta", es literalmente la dirección del usuario número 5.

REST (Representational State Transfer) es solo un conjunto de convenciones sobre cómo pedir y modificar esos recursos usando el protocolo HTTP — el mismo que usa tu navegador para cargar cualquier página. No es magia ni un lenguaje nuevo: es un acuerdo sobre cómo hablarse.

Una petición HTTP real, sin ningún framework de por medio

http 
GET /usuarios/5 HTTP/1.1
Host: api.eoi.com
Accept: application/json

--- El servidor responde ---

HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 5,
  "nombre": "Ana",
  "email": "ana@eoi.com"
}

Esto es TODO lo que pasa por la red. FastAPI, mas adelante, solo te ahorra escribir esto a mano.

Los verbos HTTP: qué quiere hacer el cliente

GET

Leer

Pide un recurso. No cambia nada en el servidor. Puedes repetirlo mil veces sin efecto secundario.

POST

Crear

Crea un recurso nuevo. Cada vez que lo repites, crea otro más (no es idempotente).

PUT

Reemplazar

Sustituye el recurso entero por lo que envías. Repetirlo dos veces da el mismo resultado.

PATCH

Modificar

Cambia solo los campos que envías, deja el resto del recurso tal cual.

DELETE

Borrar

Elimina el recurso. Repetirlo no hace nada nuevo — ya no está.

Petición y respuesta, verbo a verbo

sequenceDiagram participant C as Cliente participant S as Servidor C->>S: GET /usuarios/5 S-->>C: 200 OK + datos de Ana C->>S: POST /usuarios (nombre: Luis) S-->>C: 201 Created + nuevo usuario C->>S: PATCH /usuarios/5 (email nuevo) S-->>C: 200 OK + usuario actualizado C->>S: DELETE /usuarios/5 S-->>C: 204 No Content

Códigos de estado: la respuesta antes de leer el cuerpo

Antes de mirar los datos que devuelve el servidor, el código de 3 cifras ya te dice qué pasó. No hace falta memorizarlos todos — con el primer dígito te orientas: 2xx = todo salió bien, 4xx = el cliente hizo algo mal (pidió algo que no existe, mandó datos inválidos), 5xx = el servidor se rompió por su cuenta.

CódigoSignificaCuándo lo verás
200 OKÉxito genéricoGET, PUT, PATCH que salieron bien
201 CreatedSe creó el recursoUn POST que sale bien
204 No ContentÉxito, sin cuerpo que devolverUn DELETE que sale bien
400 Bad RequestDatos mal formadosJSON roto, campo con tipo incorrecto
401 / 403Sin autenticar / sin permisoFalta o no vale el token
404 Not FoundEse recurso no existe/usuarios/9999 si no hay usuario 9999
422 UnprocessableValidación fallóEl que más verás con FastAPI + Pydantic
500 Internal Server ErrorEl servidor petóUn bug tuyo sin capturar
INFO
Statelessness — el servidor no se acuerda de ti Cada petición HTTP se basta a sí misma: el servidor no recuerda tu petición anterior. Si necesitas que "sepa quién eres" en la siguiente, tienes que mandárselo otra vez en cada petición (normalmente un token en la cabecera Authorization). Esto es lo que hace que un servidor REST pueda repartir tus peticiones entre 10 máquinas distintas sin que a ti te afecte — ninguna "recuerda" nada, así que da igual cuál te atienda.

En resumen

  • ✓REST es un conjunto de convenciones sobre HTTP, no un lenguaje ni un framework.
  • ✓Cada recurso tiene una URL propia; el verbo (GET/POST/PUT/PATCH/DELETE) dice qué quieres hacer con él.
  • ✓El código de estado (2xx/4xx/5xx) te orienta antes de leer el cuerpo de la respuesta.
  • ✓El servidor es stateless: no recuerda tu petición anterior, se lo tienes que decir siempre.

Autoevaluación (1/1)

Q1. Llamas dos veces seguidas a DELETE /usuarios/5. ¿Qué pasa la segunda vez?

DELETE es idempotente: repetirlo no cambia el resultado. Como el recurso ya no existe, lo normal es un 404.

Tu primera API con FastAPI

  • instalación y uvicorn
  • path params
  • query params

FastAPI escribe el servidor, uvicorn lo hace correr

FastAPI es la librería con la que describes tus endpoints en Python. uvicorn es el programa que de verdad escucha en un puerto de red y le pasa cada petición a tu código FastAPI — son dos cosas distintas que se usan juntas casi siempre. Instalas ambas con un solo comando.

Hello world — 6 líneas, servidor real

bash + python 
$ pip install fastapi uvicorn
# main.py
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def leer_raiz():
    return {"mensaje": "Hola desde FastAPI"}
# Se ejecuta así, desde la carpeta de main.py:
$ uvicorn main:app --reload
# main:app -> fichero main.py, variable "app" dentro
# --reload -> reinicia solo al guardar cambios (solo en desarrollo)
# Ahora http://127.0.0.1:8000/ ya responde de verdad

Path params: parte de la URL como variable

Cuando un trozo de la URL identifica UN recurso concreto (¿cuál usuario? el 5), va como path param — entre llaves en la ruta, y como parámetro con tipo anotado en la función. FastAPI lo valida solo: si alguien pide /usuarios/hola en vez de un número, responde 422 sin que tú escribas ni un if.

Path param con validación de tipo automática

python 
@app.get("/usuarios/{usuario_id}")
def leer_usuario(usuario_id: int):
    # usuario_id ya LLEGA como int, no como string
    return {"id": usuario_id, "nombre": "Ana"}

# GET /usuarios/5      -> 200 OK, usuario_id = 5 (int)
# GET /usuarios/hola   -> 422 Unprocessable Entity
#   {"detail": [{"msg": "Input should be a valid integer", ...}]}

Nadie escribió ese 422 a mano — sale solo de anotar "usuario_id: int".

Query params: filtros y opciones, tras el "?"

Cuando NO identifican un recurso concreto sino que ajustan la petición (buscar, paginar, filtrar), van como query params: cualquier parámetro de la función que no aparezca entre llaves en la ruta, FastAPI lo busca automáticamente después del ? en la URL.

Query param opcional, con valor por defecto

python 
@app.get("/usuarios")
def listar_usuarios(activos: bool = True, limite: int = 10):
    # activos y limite: NO estan en la ruta -> son query params
    return {"activos": activos, "limite": limite}

# GET /usuarios                      -> activos=True, limite=10
# GET /usuarios?activos=false        -> activos=False, limite=10
# GET /usuarios?activos=false&limite=5
KEY
Regla rápida para no dudar ¿Identifica un recurso concreto? → path param (/usuarios/5). ¿Ajusta cómo se busca/filtra/pagina? → query param (/usuarios?activos=true). Si dudas, pregúntate: "¿esto podría faltar y la petición seguiría teniendo sentido?" — si sí, casi siempre es query param.

En resumen

  • ✓FastAPI describe los endpoints; uvicorn es quien de verdad escucha en la red.
  • ✓Los path params van entre llaves en la ruta e identifican un recurso concreto.
  • ✓Los query params van tras el "?" y ajustan/filtran la petición.
  • ✓Anotar el tipo (int, bool...) activa validación automática con 422 si no encaja.

Autoevaluación (1/1)

Q1. Quieres un endpoint que busque usuarios por texto libre, tipo /usuarios?buscar=ana. ¿Cómo declaras buscar en la función?

Cualquier parámetro de la función que no esté entre llaves en la ruta, FastAPI lo trata automáticamente como query param.

Pydantic: validación que llega gratis

  • modelos como contrato
  • el 422 con detalle
  • response_model

El problema: el JSON que llega no promete nada

Cuando alguien te manda un POST con un cuerpo JSON, ese JSON puede tener cualquier forma — un campo que falta, un número como texto, un campo de más. Sin nada que lo controle, tendrías que escribir a mano un montón de if comprobando cada campo antes de confiar en los datos. Pydantic es la librería que hace eso por ti: defines la forma que ESPERAS con una clase normal de Python, y Pydantic la usa para validar y convertir automáticamente.

Un modelo Pydantic como cuerpo de un POST

python 
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UsuarioNuevo(BaseModel):
    nombre: str
    email: str
    edad: int

@app.post("/usuarios")
def crear_usuario(usuario: UsuarioNuevo):
    # Si llegamos aqui, "usuario" YA es valido:
    # nombre es str, email es str, edad es int. Garantizado.
    return {"mensaje": f"Usuario {usuario.nombre} creado"}

No hay ni un solo "if" de validacion en esta funcion. Todo pasa antes de entrar.

Qué pasa cuando el JSON no encaja

http 
# El cliente manda esto (falta "email", "edad" es texto):
POST /usuarios
{"nombre": "Ana", "edad": "veinte"}

# FastAPI responde solo, sin que tu escribas nada:
HTTP/1.1 422 Unprocessable Entity
{
  "detail": [
    {"loc": ["body", "email"], "msg": "Field required"},
    {"loc": ["body", "edad"], "msg": "Input should be a valid integer"}
  ]
}

Dos errores, cada uno con el campo exacto y por que fallo. Esto es lo que te ahorras escribir a mano.

También controla lo que SALE: response_model

Un modelo Pydantic no es solo para lo que entra — también puedes usarlo para definir exactamente qué forma tiene lo que devuelves, con response_model. Si tu función devuelve de más (un campo interno, una contraseña hasheada), FastAPI lo filtra automáticamente y solo deja pasar lo que el modelo de salida declara.

Modelo de entrada distinto del de salida

python 
class UsuarioNuevo(BaseModel):
    nombre: str
    email: str
    password: str          # entra, pero NUNCA debe salir

class UsuarioPublico(BaseModel):
    id: int
    nombre: str
    email: str              # sin password

@app.post("/usuarios", response_model=UsuarioPublico)
def crear_usuario(usuario: UsuarioNuevo):
    nuevo_id = 42
    # Aunque devolvieramos el objeto completo con password,
    # response_model filtra y solo deja pasar lo declarado en UsuarioPublico
    return {"id": nuevo_id, **usuario.model_dump()}
WARN
422 vs 400 Con FastAPI casi siempre verás 422, no 400, cuando algo falla en la validación de datos. 400 es un error genérico "petición mal formada"; 422 significa específicamente "la petición estaba bien formada pero los datos no pasan la validación del modelo". Es una distinción de FastAPI/Pydantic, no de HTTP en general.

En resumen

  • ✓Un modelo Pydantic (BaseModel) es el contrato de qué forma tienen tus datos.
  • ✓Si el JSON no encaja con el modelo, FastAPI responde 422 con el detalle exacto, sin que escribas nada.
  • ✓response_model controla también lo que sale, y puede ocultar campos internos.

Autoevaluación (1/1)

Q1. ¿Por qué usar response_model aunque tu función ya devuelva "casi" lo correcto?

response_model es una red de seguridad: filtra la salida real al esquema declarado, evitando fugas de datos por error humano.

Probando sin escribir código: curl y REST Client

  • curl paso a paso
  • extensión REST Client de VSCode
  • ficheros .http versionables

Por qué probar a mano antes de escribir tests

Mientras estás construyendo un endpoint, quieres feedback inmediato: ¿responde lo que espero? Escribir un test automático cada vez que cambias una línea es demasiado lento en ese momento. La solución no es "abrir el navegador y hacer clicks" — para una API que no es una web, se prueba con una herramienta que hable HTTP directamente: curl desde terminal, o el plugin REST Client si trabajas en VSCode.

curl: GET, POST, y con query params

bash 
# GET simple
$ curl http://127.0.0.1:8000/usuarios/5

# GET con query params
$ curl "http://127.0.0.1:8000/usuarios?activos=true&limite=5"

# POST con cuerpo JSON
$ curl -X POST http://127.0.0.1:8000/usuarios \
    -H "Content-Type: application/json" \
    -d '{"nombre": "Ana", "email": "ana@eoi.com", "edad": 20}'

# Con cabecera de autenticacion (token de ejemplo)
$ curl http://127.0.0.1:8000/perfil \
    -H "Authorization: Bearer eyJhbGciOi..."

-X indica el verbo, -H añade cabeceras, -d el cuerpo. Con GET (por defecto) no hace falta -X.

REST Client: probar la API sin salir de VSCode

Es una extensión de VSCode (busca REST Client, de Huachao Mao, id humao.rest-client). Escribes tus peticiones en un fichero de texto normal con extensión .http, y encima de cada una aparece un enlace "Send Request" — lo clicas y la respuesta se abre al lado, con status code y JSON formateado. Nada que instalar aparte de la extensión, nada que memorizar de sintaxis curl.

peticiones.http — varias peticiones en un solo fichero

http 
@baseUrl = http://127.0.0.1:8000

### Listar usuarios activos
GET {{baseUrl}}/usuarios?activos=true

### Ver un usuario concreto
GET {{baseUrl}}/usuarios/5

### Crear un usuario nuevo
POST {{baseUrl}}/usuarios
Content-Type: application/json

{
  "nombre": "Ana",
  "email": "ana@eoi.com",
  "edad": 20
}

### Borrar un usuario
DELETE {{baseUrl}}/usuarios/5

Cada bloque separado por "###" es una petición independiente con su propio botón "Send Request" en VSCode. "@baseUrl" es una variable reutilizable.

KEY
La ventaja real del .http curl es perfecto para una comprobación rápida y suelta. Un fichero .http se guarda en el repositorio junto al código, queda versionado en git, y cualquiera del equipo lo abre y prueba la misma petición exacta sin tener que reconstruir el comando curl de memoria cada vez. Muchos proyectos guardan un peticiones.http junto al README, como documentación viva de ejemplo.

En resumen

  • ✓curl -X, -H y -d son suficientes para probar cualquier verbo desde terminal.
  • ✓REST Client (VSCode) permite probar con un clic desde un fichero .http normal.
  • ✓Los ficheros .http se versionan en git — documentación viva y reproducible.

Documentación que se genera sola

  • /docs — Swagger UI
  • /redoc
  • de dónde sale: openapi.json

Dos documentaciones interactivas, sin escribir una línea

Arranca cualquier API de FastAPI y visita /docs en el navegador: verás cada endpoint, cada parámetro, cada modelo de entrada/salida, y un botón "Try it out" para probarlo directamente ahí, sin curl ni REST Client. Es Swagger UI. /redoc muestra lo mismo con un formato de lectura distinto, más pensado para consultar que para probar.

De dónde sale exactamente: tu código ES la documentación

Nadie escribe /docs a mano. FastAPI lee tus type hints y tus modelos Pydantic, y con eso construye automáticamente un documento llamado schema OpenAPI (disponible en crudo en /openapi.json). Swagger UI y ReDoc son solo visores bonitos de ESE documento. Si cambias un tipo en tu código, la documentación cambia sola en el siguiente arranque — no hay forma de que se desincronice, porque no la escribiste dos veces.

El endpoint de usuarios, visto desde openapi.json

json 
// Fragmento real de /openapi.json para POST /usuarios
{
  "paths": {
    "/usuarios": {
      "post": {
        "requestBody": {
          "content": {"application/json": {
            "schema": {"$ref": "#/components/schemas/UsuarioNuevo"}
          }}
        },
        "responses": {"200": {"description": "Successful Response"}}
      }
    }
  },
  "components": {"schemas": {"UsuarioNuevo": {
    "properties": {
      "nombre": {"type": "string"},
      "email": {"type": "string"},
      "edad": {"type": "integer"}
    },
    "required": ["nombre", "email", "edad"]
  }}}
}

Esto es literalmente tu clase "UsuarioNuevo(BaseModel)" traducida a JSON. Swagger UI solo lo pinta bonito.

INFO
Para qué sirve esto en la práctica Si trabajas con un equipo de frontend, o compartes tu API con otro equipo, /docs es la referencia — no necesitas mandar un Word explicando los endpoints. Y con "Try it out" pueden probar la API real ahí mismo antes de escribir ni una línea de código cliente.

Autoevaluación (1/1)

Q1. Cambias un campo de tu modelo Pydantic de str a int. ¿Qué tienes que hacer para que /docs lo refleje?

La documentación se deriva del código en cada arranque — nunca se puede desincronizar porque nunca se escribió aparte.

FastAPI vs Flask: por qué es una evolución

  • el mismo endpoint, dos formas
  • WSGI vs ASGI
  • Depends()

Flask (2010) y FastAPI (2018): contextos distintos

Flask es anterior a que Python tuviera async/await maduro y a que los type hints fueran algo habitual. Es minimalista a propósito: te da el enrutado y poco más, tú añades el resto con extensiones. FastAPI nació después, diseñado desde cero para aprovechar type hints (validación y docs gratis) y async nativo (más peticiones simultáneas con menos recursos). No es que Flask esté "mal" — es una generación de diseño distinta.

El mismo endpoint: crear usuario, en Flask

python 
from flask import Flask, request, jsonify

app = Flask(__name__)

@app.route("/usuarios", methods=["POST"])
def crear_usuario():
    data = request.get_json()

    # Validacion manual, campo a campo
    if "nombre" not in data or not isinstance(data["nombre"], str):
        return jsonify({"error": "nombre invalido"}), 400
    if "edad" not in data or not isinstance(data["edad"], int):
        return jsonify({"error": "edad invalida"}), 400

    return jsonify({"mensaje": f"Usuario {data['nombre']} creado"}), 201

Sin documentacion automatica. Sin validacion de tipos real (isinstance no distingue "20" de 20 salvo que lo compruebes tu).

El mismo endpoint, en FastAPI

python 
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class UsuarioNuevo(BaseModel):
    nombre: str
    edad: int

@app.post("/usuarios", status_code=201)
def crear_usuario(usuario: UsuarioNuevo):
    return {"mensaje": f"Usuario {usuario.nombre} creado"}

# La validacion de arriba (los dos "if") desaparece entera.
# Y /docs documenta este endpoint solo, sin hacer nada mas.

Mismo comportamiento, sin la validacion manual — y con documentacion interactiva de regalo.

Comparación directa

FlaskFastAPI
Validación de datosManual (a mano, por ti)Automática (Pydantic)
Documentación interactivaNo, salvo extensión aparte/docs y /redoc de fábrica
Async nativoLimitado (WSGI, síncrono)Nativo (ASGI)
Inyección de dependenciasNo hay sistema propioDepends() integrado
Curva de entradaMuy simple para algo pequeñoUn poco más de conceptos al empezar
Madurez del ecosistemaMuy amplio, 15 añosMás joven, creciendo rápido

Depends(): inyección de dependencias de fábrica

Ya usaste Depends() sin nombrarlo tanto si has hecho el curso de mocking de este bootcamp: es como FastAPI resuelve "qué objeto le paso a este endpoint" — una base de datos, el usuario autenticado, un cliente HTTP — sin que la función tenga que crearlo ella misma. Eso es justo lo que permite sustituir esas dependencias por versiones falsas en los tests con app.dependency_overrides, como viste en el laboratorio de mocking. Flask no trae un sistema equivalente integrado.

En resumen

  • ✓FastAPI convierte type hints en validación real y documentación automática; en Flask eso se escribe a mano.
  • ✓FastAPI es ASGI (async nativo); Flask es WSGI (síncrono por defecto).
  • ✓Depends() es el sistema de inyección de dependencias que hace testeable la API sin tocar código real.
  • ✓Flask sigue siendo válido para cosas simples — FastAPI gana cuando el contrato de datos importa.

Autoevaluación (1/1)

Q1. ¿Cuál es la diferencia real entre isinstance(data["edad"], int) a mano en Flask, y edad: int en un modelo Pydantic?

La validación en sí puede ser parecida, pero Pydantic añade documentación automática y mensajes de error estructurados y consistentes, gratis.

Ejercicio final: pruébalo tú mismo

  • construir el endpoint
  • probarlo a mano
  • testearlo de verdad (mocking)

El objetivo: cerrar el círculo con lo que ya sabes

Vas a construir un endpoint GET /convertir?de=EUR&a=USD&cantidad=100 que llama a un servicio externo de tipos de cambio y devuelve el resultado. Es prácticamente el mismo escenario del laboratorio del curso de mocking (el de tipos de cambio) — pero esta vez lo construyes tú, lo pruebas a mano, y lo testeas de verdad. Nada de esto es nuevo: es aplicar los capítulos 1-6 de este curso más lo que ya construiste en el laboratorio de mocking.

🟡 Andamiaje (1/2)

Construye el endpoint y pruébalo a mano.

Paso 1 — Construir (20 min):
Crea GET /convertir con query params de: str, a: str, cantidad: float. Usa Depends() para inyectar un cliente HTTP (como en el laboratorio de mocking) que llama a un servicio externo de tipos de cambio. Devuelve un modelo Pydantic con de, a, cantidad_original, cantidad_convertida.

Paso 2 — Probarlo a mano (10 min):
Arranca con uvicorn. Pruébalo con curl Y con un fichero .http en REST Client — al menos una petición válida y una con un parámetro que falte, para ver el 422 real. Abre /docs y confirma que el endpoint aparece bien documentado, con "Try it out" funcionando.

🟡 Andamiaje (2/2)

Testéalo de verdad, sin red real.

Paso 3 — Testearlo de verdad (20 min):
Escribe un test con TestClient + app.dependency_overrides que sustituya el cliente HTTP real por un httpx.MockTransport — exactamente el patrón del laboratorio de mocking, sin inventar nada nuevo. El test no debe abrir ni un socket real.

Entrega: main.py con el endpoint, peticiones.http con al menos 2 peticiones, y test_convertir.py con al menos un test que pase sin red real.

💡 Pista

Si te atascas en el Paso 3, vuelve al Laboratorio del curso de mocking — el patrón de MockTransport + dependency_overrides es literalmente el mismo, solo cambia el nombre de los campos.

KEY
Por qué este ejercicio importa más que "otro CRUD" Un endpoint que llama a algo externo (y falla, o tarda, o cambia de formato) es el caso real del 90% de las APIs que vas a construir en el trabajo. Saber probarlo a mano (curl/REST Client), documentarlo solo (Pydantic + /docs), y testearlo sin depender de que el servicio externo esté vivo (mocking) es exactamente el ciclo completo de este bootcamp.
